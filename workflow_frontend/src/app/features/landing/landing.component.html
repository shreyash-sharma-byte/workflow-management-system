Workflow platform

Enterprise Workflow Management

A workflow is authored once as a template of stations, typed tasks and directed transitions, then executed as tracked instances by a server-side engine that gates every move by role, pins the version, and writes an append-only audit trail. Built for teams that need a workflow to move exactly as designed — and to be able to prove it did.

What happens when an instance runs

  1. Select a published version. POST /api/v1/instances/ resolves the template's current_version — the frozen publish snapshot, never a live draft. Editing a published template runs create_draft, which deep-clones the snapshot into a new version; publish freezes it. An instance pins its template_version with on_delete=PROTECT, so editing a template never mutates the version a running instance holds.
  2. The engine creates the instance. WorkflowEngine.create_instance finds the START station (refusing with no_start_station if none), writes the instance as ACTIVE at that station with a generated reference (WF-N), version=1, a UUID public_token, an INSTANCE_CREATED history row, and a PENDING TaskExecution for every task at the start station.
  3. Only the station's roles can act. IsStationOwner on the task and move endpoints, and _validate_user_permission inside the engine, both intersect the caller's Django groups with station.allowed_roles. A mismatch is a server-side 403 — independent of what the UI hides.
  4. Tasks run a state machine. PENDING → IN_PROGRESS → COMPLETED via start and submit. submit validates the response against the task's task_config schema — FORM required fields, CONFIRMATION required checklist items, DOCUMENT min_files, APPROVAL decision must be one of the configured options — then writes TASK_COMPLETED.
  5. A move is five ordered checks. POST /api/v1/instances/:id/move/ enters WorkflowEngine.move: the instance is ACTIVE, the caller holds a role at the current station, a Transition exists from current to target (else 400 with allowed_transitions), every is_required task is COMPLETED (else tasks_incomplete with the pending list), and the optimistic lock matches.
  6. The move is atomic and rejects stale writes. _execute_move runs in one transaction.atomic(): it updates current_station only where the row's version still equals the one it read — zero rows matched returns 409 concurrency_conflict, so two users can't double-move — then bumps version = version + 1, writes a MOVED history row, auto-creates the new station's PENDING tasks, and notifies the new station's roles.
  7. Approval, rejection, completion. An APPROVAL task stores its decision (validated against the version's options — default Approved / Rejected) in response_data and the audit trail; the outcome is data, not a hidden branch — what happens next is the transition the station actor takes. Reaching an END station flips status → COMPLETED and stamps completed_at (INSTANCE_COMPLETED); cancel is the other exit — ACTIVE → CANCELLED, with the reason written to history.
  8. The audit trail is append-only. INSTANCE_CREATED, TASK_STARTED, TASK_COMPLETED, MOVED, DOCUMENT_UPLOADED, INSTANCE_CANCELLED and INSTANCE_COMPLETED each append a WorkflowInstanceHistory row carrying actor, from/to station, task, remarks and a metadata summary. Its save() raises on any update, and Document.delete() raises too — the trail can't be edited, not even by an admin or the ORM.

Roles & permissions

Nine realm roles, enforced server-side — not by hiding UI. DRF permission classes gate the endpoint, the engine re-checks inside move and submit, and Keycloak is the source of truth: realm_access.roles is synced to Django Groups on every request, so a removed role is gone on the next call.

  • ADMINFull CRUD on templates and publish; create, move and cancel any instance; execute any task.
  • PM_TEAMCreate instances (IsInitiator); no template or station write access; sees the instances it initiated.
  • PM_MANAGERCreate instances; no template write access; sees its own initiated instances.
  • DEV_TEAMExecute tasks and move at stations whose allowed_roles include DEV_TEAM (IsStationOwner).
  • DEV_LEADExecute tasks and move at stations listing DEV_LEAD.
  • QA_TEAMExecute tasks and move at stations listing QA_TEAM.
  • QA_MANAGERExecute tasks and move at stations listing QA_MANAGER.
  • DEV_OPSExecute tasks and move at stations listing DEV_OPS.
  • AUDITORRead-only: sees all instances and history, but cannot create, move or execute.

Data model

  • WorkflowTemplateDRAFT / PUBLISHED / ARCHIVED metadata; points at current_version and draft_version.
  • WorkflowTemplateVersionImmutable publish snapshot; unique (template, version_number); next_draft links the fork chain.
  • StationA stage with START / NORMAL / END type; allowed_roles (M2M to Group) gates who may act.
  • TransitionDirected from_station → to_station edge; remarks_required flag; unique per version.
  • TaskDefinitionTyped task config (task_type, is_required, task_config JSON); allowed_roles subset of the station's.
  • WorkflowInstanceThe run. Source of truth for status: ACTIVE / COMPLETED / CANCELLED / BLOCKED are declared; the engine writes ACTIVE on create, COMPLETED on END, CANCELLED on cancel.
  • TaskExecutionRuntime task with PENDING / IN_PROGRESS / COMPLETED / FAILED / SKIPPED status; response_data; its own version lock.
  • WorkflowInstanceHistoryAppend-only audit (9 action types); save() raises on update.
  • DocumentImmutable file trail; delete() raises.
  • Notification · UserIn-app events per recipient; User is auto-provisioned from the Keycloak sub claim.

Decisions, not just features

  • Immutable snapshots + draft forkingA published template is frozen; edits clone into a new draft version and publish links the old via next_draft. Instances hold their version with on_delete=PROTECT, so a running workflow can't be corrupted by a template edit.
  • Optimistic locking by integer versionUPDATE … WHERE version = ? returns zero rows on a stale write, which the engine turns into a 409 concurrency_conflict — never a silent double-move.
  • Append-only enforced in the modelWorkflowInstanceHistory.save() and Document.delete() both raise. Immutability is a constraint, not a convention — no admin or ORM path can edit the trail.
  • Roles are a server boundary, twiceDRF permission classes gate the endpoint and the engine re-checks inside move / submit, so a 403 is returned by the API even when a route is reached directly.
  • One engine, one transactionMove, history write, status flip and new-task creation commit together in transaction.atomic(), so a crash can't leave a half-moved instance.
  • Publish-time graph validationpublish refuses a template without exactly one START, at least one END, or with a stranded station that has no outgoing transition — a workflow that can't complete can't be shipped.
